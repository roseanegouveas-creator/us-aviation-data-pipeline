# SPEC — TRANSFORMAÇÃO | US AVIATION DATA PIPELINE

## CONTEXTO

Estou construindo um pipeline de dados em Python para analisar operações aéreas nos Estados Unidos.

O projeto trabalha com dados de companhias aéreas, aeroportos, estatísticas diárias e registros individuais de voos.

O foco analítico é:
- Atrasos de voos.
- Cancelamentos.
- Desempenho das companhias aéreas.
- Desempenho dos aeroportos.
- Causas de atrasos.
- Indicadores operacionais por período.

Trabalho com spec-driven development: esta SPEC é a fonte da verdade e o código é consequência dela.

Não acrescente requisitos que não estejam escritos aqui. Se alguma regra estiver ambígua, pergunte antes de escrever código.

## STACK

- Python 3.13 (versão mínima única do projeto; `pyproject.toml` com `requires-python = ">=3.13"` e `.python-version` fixando 3.13).
- Dependências gerenciadas com uv.
- DuckDB como banco de dados.
- Pandas disponível para manipulação quando necessário.
- SQL do DuckDB para conversão e transformação dos dados.
- Banco: aviation.duckdb na raiz do projeto.
- Nenhum orquestrador. Script executável pela linha de comando.

### Regras de tipagem

Datas:

- data_voo: DATE.
- data_primeiro_voo: DATE.
- data_ultimo_voo: DATE.
- data_ingestao: TIMESTAMPTZ.

Contagens:

- Quantidades de voos, aeroportos, cancelamentos e desvios devem utilizar BIGINT quando especificado.
- Indicadores binários devem utilizar INTEGER ou BOOLEAN conforme o mapa.

Valores decimais:

- Coordenadas geográficas devem utilizar DECIMAL(10,6).
- Taxas e percentuais devem utilizar DECIMAL(8,5).
- Atrasos e tempos decimais devem utilizar DECIMAL(10,2), exceto atraso_medio_partida, que utiliza DECIMAL(10,4).

Identificadores:

- codigo_companhia, codigo_iata, codigo_icao, numero_matricula_aeronave, origem e destino permanecem VARCHAR.

Motivo: códigos de companhias, aeroportos e aeronaves são identificadores, não números para operações matemáticas.

Horários:

- horario_partida_programado, horario_partida_real, horario_decolagem, horario_pouso, horario_chegada_programado e horario_chegada_real permanecem INTEGER.
- Não converter automaticamente esses campos para TIME.

Motivo: os dados utilizam representação numérica HHMM, e a conversão para horário exigiria regras adicionais para valores especiais, horários após a meia-noite e eventuais valores inválidos.

## 4. CONVERSÃO E VALIDAÇÃO ESTRITA

Toda conversão deve ser estrita.

Utilizar CAST e funções explícitas do DuckDB.

Não utilizar:

- TRY_CAST.
- TRY_STRPTIME.
- errors="coerce".
- Conversões que transformem valores inválidos silenciosamente em NULL.

Todas as conversões numéricas e de datas devem validar o formato original antes de executar a conversão.

Não basta utilizar CAST diretamente, pois o DuckDB pode arredondar ou interpretar valores que não correspondem ao formato esperado. Exemplos verificados no DuckDB:

- `CAST('1.5' AS INTEGER)` devolve 2.
- `CAST('1.234' AS DECIMAL(10,2))` devolve 1.23.
- `CAST('2025-01-01 10:00' AS DATE)` devolve 2025-01-01, descartando a hora.

Regras:

- INTEGER: rejeitar casas decimais, inclusive quando o valor puder ser arredondado pelo DuckDB.
- BIGINT: mesma regra de INTEGER.
- DECIMAL(p,s): rejeitar mais casas decimais do que a escala s. Não arredondar.
- DECIMAL(p,s): rejeitar mais de p − s dígitos inteiros, para evitar overflow. Zeros à esquerda não contam para esse limite.
- DATE: aceitar somente o formato YYYY-MM-DD.
- TIMESTAMPTZ: aceitar somente o formato `YYYY-MM-DD HH:MM:SS[.ffffff]±HH[:MM]`. Data, hora e fuso horário são obrigatórios; até 6 casas de fração de segundo.
- Notação científica, como 1e3, não será aceita.
- Espaços nas extremidades e sinais + e - serão aceitos nos números. Datas e timestamps não aceitam espaços nas extremidades.

Exemplos:

| Valor original | INTEGER | DECIMAL(10,2) |
|---|---|---|
| 10 | Aceita | Aceita |
| 1.5 | Rejeita | Aceita |
| 1.234 | Rejeita | Rejeita |
| +10 | Aceita | Aceita |
| -10 | Aceita | Aceita |
| " 10 " (com espaços) | Aceita | Aceita |
| 1e3 | Rejeita | Rejeita |
| 123456789.1 | Rejeita | Rejeita (9 dígitos inteiros; máximo 8) |

Quando uma conversão não atender ao formato, utilizar error() no SQL do DuckDB para interromper a execução.

Ao falhar uma conversão:

1. Identificar a tabela.
2. Identificar a coluna.
3. Apresentar um exemplo do valor inválido.
4. Executar ROLLBACK.
5. Encerrar com sys.exit(1).

Motivo: um NULL ou valor alterado pela conversão fica indistinguível do dado verdadeiro recebido na origem. A conversão não pode esconder problemas nos dados.

### 4.1 BOOLEAN

Para as colunas booleanas, utilizar CAST direto do DuckDB.

São aceitos os formatos reconhecidos pelo DuckDB, incluindo:

- 0 e 1
- true e false
- t e f
- yes e no

A base atual apresenta 0 e 1.

Motivo: esses formatos são inequívocos; o CAST rejeita qualquer outro valor (por exemplo, 2) sem arredondar.

### 4.2 Exceção: coordenadas geográficas

latitude e longitude (DECIMAL(10,6)) podem receber mais de 6 casas decimais e são arredondadas para 6 casas pelo CAST.

As demais regras continuam valendo para essas colunas: no máximo 4 dígitos inteiros, sem notação científica.

Motivo: 73 de 361 aeroportos possuem de 13 a 15 casas decimais (por exemplo, 35.2140007019043), que são ruído de representação em ponto flutuante de 32 bits. Seis casas equivalem a cerca de 11 cm. Sem esta exceção, a transformação nunca seria concluída com os dados atuais.

## 5. DUPLICATAS E CHAVES

Nenhuma duplicidade deve ser removida sem uma regra documentada.

Chaves:

| Tabela | Chave | Situação |
|---|---|---|
| companhias_aereas | codigo_companhia | Validada |
| aeroportos | codigo_iata | Validada |
| estatisticas_diarias_aeroportos | data_voo + aeroporto | Validada |
| voos_2025 | data_voo + codigo_companhia + numero_voo + origem + destino + horario_partida_programado | **Provisória** |

A chave de voos_2025 não apresentou repetições na amostra (120.000 registros), mas ainda não foi validada na base completa.

A identificação de linhas integralmente repetidas e de conflitos deve considerar todas as colunas da tabela, inclusive:

- arquivo_origem
- data_ingestao

Não comparar somente as colunas de negócio.

Política de duplicidade (**provisória**, até a validação da base completa):

- Linhas integralmente repetidas devem ser identificadas e contabilizadas.
- Chaves repetidas com conteúdos diferentes devem ser apresentadas como conflitos, com contagem e até 5 exemplos.
- Não escolher automaticamente um registro conflitante.
- Não eliminar registros.
- A presença de duplicidades ou conflitos não interrompe a execução.

Motivo: a transformação não pode decidir silenciosamente qual registro representa a informação correta.

## 7. METADADOS DE INGESTÃO

As colunas abaixo devem ser preservadas e traduzidas, nas quatro tabelas REFINED:

| RAW | REFINED |
|---|---|
| _source_file | arquivo_origem |
| _ingested_at | data_ingestao |

Tipos:

- arquivo_origem: VARCHAR.
- data_ingestao: TIMESTAMPTZ.

A transformação deve preservar esses metadados exatamente como estão em RAW, sem alterar sua origem:

- arquivo_origem recebe o valor de `_source_file`, que, pela Ingestão SPEC (seção 2.1), é o nome real do arquivo lido. A transformação não recalcula, substitui nem corrige esse valor.
- data_ingestao recebe o valor de `_ingested_at` convertido para TIMESTAMPTZ. Nos arquivos atuais, esse valor registra o momento da exportação anterior ao pipeline (Ingestão SPEC, seção 2.2).

Motivo: esses campos permitem rastrear a origem do registro e o momento em que foi ingerido.

Não remover os metadados durante a transformação.

## 8. SAÍDA NA TELA

Uma linha por tabela, no formato:

```text
refined.companhias_aereas                 X -> X linhas
refined.aeroportos                        X -> X linhas
refined.estatisticas_diarias_aeroportos   X -> X linhas
refined.voos_2025                         X -> X linhas

TOTAL                                     X -> X linhas
```

Abaixo de cada tabela, apresentar:

- Quantidade de registros na origem.
- Quantidade de registros no destino.
- Quantidade de linhas integralmente repetidas.
- Quantidade de conflitos de chave, com até 5 exemplos.
- Quantidade de nulos mantidos por coluna.

A listagem de nulos deve apresentar somente as colunas que possuem valores nulos.

Quando nenhuma coluna possuir nulos, apresentar:

```text
Nulos mantidos: nenhum
```

As contagens devem vir diretamente do banco DuckDB.

Separar milhares utilizando ponto.

Reconfigurar stdout para UTF-8.

Motivo: a saída é o instrumento de conferência da transformação e deve permitir identificar diferenças entre RAW e REFINED.

## 9. REEXECUÇÃO

Utilizar CREATE OR REPLACE TABLE.

Nunca acrescentar registros de uma execução anterior.

Executar dez vezes deve produzir o mesmo resultado de uma única execução, considerando a mesma origem.

Motivo: permitir reexecuções durante o desenvolvimento sem acumular dados.

## 10. ERRO

Antes de iniciar a transformação, verificar a existência das quatro tabelas:

- raw.airlines
- raw.airports
- raw.daily_airport_stats
- raw.flights_2025

Se faltar qualquer tabela:

1. Informar todas as tabelas ausentes.
2. Orientar a execução de:

```powershell
uv run python -m pipeline.ingestao
```

3. Encerrar com sys.exit(1).
4. Não realizar transformação parcial.

Motivo: impedir que o banco REFINED seja atualizado parcialmente.

## 11. TRANSAÇÃO E ATOMICIDADE

As quatro tabelas devem ser transformadas dentro de uma única transação.

Fluxo:

1. Iniciar transação.
2. Transformar as quatro tabelas.
3. Validar as contagens de registros.
4. Validar os nulos.
5. Confirmar a transação somente se todas as validações passarem.
6. Em qualquer falha, executar ROLLBACK.

Motivo: impedir que uma falha na quarta tabela deixe as três primeiras atualizadas e a quarta desatualizada.

## 12. INTEGRIDADE RAW × REFINED

Após cada transformação, comparar:

- Quantidade de linhas na origem e no destino.
- Quantidade de nulos em cada coluna correspondente.

Se qualquer contagem divergir:

- Informar tabela e coluna.
- Apresentar quantidade esperada e quantidade encontrada.
- Executar ROLLBACK.
- Encerrar com sys.exit(1).

Motivo: a camada REFINED precisa preservar a integridade dos registros recebidos.
