# SPEC.md — US Aviation Data Pipeline 2025

## 1. CONTEXTO DO PROJETO

Estou construindo um pipeline de dados em Python para analisar voos realizados nos Estados Unidos durante o ano de 2025.

O projeto utiliza dados públicos relacionados a companhias aéreas, aeroportos, estatísticas diárias dos aeroportos e registros individuais de voos.

O foco analítico é:
- Atrasos de voos.
- Voos cancelados.
- Desempenho das companhias aéreas.
- Desempenho dos aeroportos.
- Estatísticas diárias de movimentação e operação.

Trabalho com **spec-driven development**: esta SPEC é a fonte da verdade e o código é consequência dela.

Não acrescente requisitos que não estejam escritos aqui. Se alguma regra de negócio estiver ambígua, pergunte antes de implementar.

# SPEC DO pipeline/db.py

## Objetivo

Criar um módulo central responsável exclusivamente pela conexão com o DuckDB, criação de schemas e gravação de DataFrames.

As etapas seguintes importarão este módulo.

### D1. CAMINHOS

O caminho do banco `aviation.duckdb` deve ser resolvido a partir da localização do próprio `db.py`, considerando que ele está dentro de `pipeline/`.

O banco deve ser criado na raiz do projeto, um nível acima de `pipeline/`.

A pasta RAW deve ser identificada pelo nome `Raw`, respeitando a estrutura existente.

Motivo: executar um script a partir de outra pasta não pode criar um banco vazio no local errado.

### D2. FUNÇÕES E CONSTANTES

O módulo deve expor exatamente:

- `PASTA_RAW`: Path da pasta Raw.
- `conectar()`: abre o banco DuckDB, criando-o caso não exista.
- `criar_schema(con, nome)`: executa CREATE SCHEMA IF NOT EXISTS.
- `gravar(con, df, schema, tabela)`: grava o DataFrame e devolve a quantidade de registros efetivamente gravados.

Não implementar outras regras de negócio neste módulo.

O `db.py` não deve:
- Ler arquivos CSV.
- Conhecer os nomes das tabelas.
- Fazer conversões de tipos.
- Limpar dados.
- Excluir registros.
- Imprimir mensagens de execução.

Motivo: cada etapa deve decidir suas próprias regras. O módulo de conexão precisa ser reutilizável.

### D3. GRAVAÇÃO

A função `gravar()` deve:

1. Receber uma conexão DuckDB.
2. Receber um DataFrame.
3. Receber o nome do schema e da tabela.
4. Recriar a tabela utilizando CREATE OR REPLACE TABLE.
5. Preservar as colunas e os tipos existentes no DataFrame.
6. Devolver a quantidade de registros consultada diretamente no banco por SELECT COUNT(*).

Não deixar views ou tabelas temporárias desnecessárias.

Motivo: a contagem exibida precisa representar o conteúdo efetivamente gravado no banco.

### D4. CONEXÃO

A função `conectar()` devolve uma conexão aberta.

Quem chama a função é responsável por fechar a conexão.

Não manter conexão global.

### CRITÉRIOS DE ACEITE — db.py

- Importar `pipeline.db` não abre o banco nem cria arquivos.
- Executar `conectar()` a partir de outra pasta cria `aviation.duckdb` na raiz do projeto.
- A função `criar_schema()` cria schemas sem gerar erro quando eles já existem.
- Gravar um DataFrame de três registros devolve três.
- Executar a gravação novamente substitui os registros anteriores, sem duplicar dados.

# SPEC DO pipeline/ingestao.py

## Objetivo

Realizar a ingestão dos quatro arquivos CSV originais para o schema RAW do DuckDB.

A ingestão representa a entrada dos dados no pipeline, sem aplicar regras de transformação.

### 1. ESCOPO E NOMES

Schema de destino:

`raw`

Mapa de arquivos para tabelas, completo e literal:

| Arquivo | Tabela de destino |
|---|---|
| airlines.csv | airlines |
| airports.csv | airports |
| daily_airport_stats.csv | daily_airport_stats |
| flights_2025_sample.csv | flights_2025 |

O arquivo `flights_sample.csv` NÃO deve ser importado.

Motivo: ele será mantido fora do escopo da ingestão. O pipeline utilizará os quatro arquivos definidos acima.

### 2. PROIBIÇÕES

Durante a ingestão:

- Nenhuma conversão de tipos.
- Nenhuma linha descartada.
- Nenhuma deduplicação.
- Nenhuma coluna renomeada.
- Nenhum valor corrigido (única exceção: a coluna de controle `_source_file`, seção 2.1).
- Nenhum preenchimento de campos nulos.
- Nenhuma normalização de dados.
- Nenhuma aplicação de regras de negócio.

Motivo: RAW deve representar os dados recebidos, preservando a fronteira entre o dado original e o dado tratado.

As transformações serão responsabilidade de uma etapa posterior, de RAW para REFINED.

### 2.1 METADADO DE ORIGEM (_source_file)

`_source_file` é uma coluna de controle do pipeline, e não um dado recebido. Ela deve registrar o nome real do arquivo que forneceu os dados à camada RAW.

Regras:

- A ingestão preenche `_source_file` com o nome do arquivo lido na pasta `Banco/` (somente o nome, sem caminho), em todas as linhas das quatro tabelas.
- Se a origem for `flights_2025_sample.csv`, esse é o valor registrado.
- Se a origem passar a ser `flights_2025.csv`, o valor registrado muda automaticamente, pois é derivado do mapa de arquivos da seção 1.
- Não é permitido registrar um nome fictício, genérico ou herdado de uma etapa anterior ao pipeline (por exemplo, `flights.parquet`).
- O valor de `_source_file` presente no CSV é substituído pelo nome do arquivo lido. A coluna mantém o nome e a posição originais.
- Se um arquivo não possuir a coluna `_source_file`, ela é acrescentada como última coluna.
- Nenhuma outra coluna é alterada por esta regra.

Motivo: o metadado de origem existe para rastrear de qual arquivo cada registro entrou no pipeline. Um nome herdado de uma exportação anterior aponta para um arquivo que o pipeline nunca leu, quebrando a rastreabilidade. Como o valor é gerado pelo pipeline, e não recebido, preenchê-lo não é correção de dado.

As etapas seguintes (RAW → REFINED) devem preservar esse metadado sem alterá-lo.

### 2.2 MOMENTO DA INGESTÃO (_ingested_at)

`_ingested_at` permanece exatamente como recebido no CSV. A ingestão não gera nem altera esse valor.

Motivo: manter a ingestão reprodutível (seção 3); um valor gerado a cada execução faria duas execuções produzirem resultados diferentes.

Pendência conhecida: nos arquivos atuais, `_ingested_at` registra o momento da exportação anterior ao pipeline, e não o momento da ingestão realizada por `pipeline/ingestao.py`. A semântica definitiva dessa coluna depende de decisão posterior.

### 3. REEXECUÇÃO

A ingestão deve ser idempotente.

Executar o script várias vezes deve produzir o mesmo resultado de uma única execução.

As tabelas devem ser recriadas utilizando CREATE OR REPLACE TABLE.

Nunca utilizar INSERT para acrescentar os dados de uma execução anterior.

Motivo: permitir reexecuções durante o desenvolvimento sem gerar duplicidades.

### 4. LEITURA DOS ARQUIVOS

Os arquivos devem ser lidos diretamente da pasta `Banco/`.

Configurações:

- Utilizar Pandas.
- Encoding declarado como UTF-8.
- Não realizar detecção automática de encoding.
- Não descompactar arquivos, pois os arquivos são CSVs comuns.
- Não modificar os arquivos originais.

Campos vazios devem continuar representando valores nulos.

Não transformar campos vazios em strings vazias nem converter valores textuais especiais em nulos por inferência automática.

Motivo: preservar o conteúdo original e evitar interpretações indevidas durante a ingestão.

### 5. TIPAGEM

Todas as colunas devem ser importadas como texto.

Utilizar:

`dtype=str`

A inferência automática de tipos deve permanecer desativada.

Exemplos:

- Datas permanecem texto.
- Horários permanecem texto.
- Quantidades permanecem texto.
- Identificadores permanecem texto.
- Valores numéricos permanecem texto.

Motivo: a conversão de tipos deve acontecer na camada REFINED, onde as decisões de transformação serão documentadas.

### 6. SAÍDA NA TELA

A execução deve apresentar uma linha para cada tabela importada.

Formato esperado:

```text
RAW.airlines                 | X registros
RAW.airports                 | X registros
RAW.daily_airport_stats      | X registros
RAW.flights_2025             | X registros

TOTAL                        | X registros
```

Regras:

- As contagens devem ser obtidas diretamente do DuckDB.
- Não utilizar a quantidade de linhas do DataFrame como resultado final.
- Separar milhares utilizando ponto.
- Exibir o nome qualificado do schema e da tabela.
- Reconfigurar stdout para UTF-8.

O total deve representar a soma das quatro tabelas importadas.

Não existe uma quantidade total de registros previamente fixada nesta SPEC. O total correto será determinado pelos arquivos existentes.

### 7. TRATAMENTO DE ERROS

Antes de abrir o banco, verificar se os quatro arquivos obrigatórios existem.

Se algum estiver faltando:

1. Informar quais arquivos estão ausentes.
2. Informar o caminho da pasta onde foram procurados.
3. Encerrar a execução utilizando `sys.exit(1)`.
4. Não realizar ingestão parcial.
5. Não criar ou modificar nenhuma tabela.

Motivo: impedir que um banco parcialmente atualizado seja interpretado como uma ingestão completa.

### 8. EXECUÇÃO

O módulo deve ser executável por:

```powershell
uv run python -m pipeline.ingestao
```

O script deve encerrar automaticamente após concluir a ingestão.

Não manter processos ativos.

### CRITÉRIOS DE ACEITE — INGESTÃO

- Importar exatamente quatro arquivos.
- Não importar `flights_sample.csv`.
- Criar as quatro tabelas no schema RAW.
- Todas as colunas devem entrar como VARCHAR.
- Nenhuma transformação deve ocorrer, exceto o preenchimento de `_source_file` (seção 2.1).
- Em todas as linhas das quatro tabelas, `_source_file` é igual ao nome do arquivo lido.
- Nenhuma linha de `raw.flights_2025` registra `flights.parquet` ou outro nome que não seja o arquivo lido.
- `_ingested_at` é idêntico ao valor do CSV.
- As contagens exibidas devem vir do banco.
- Executar duas vezes deve produzir o mesmo resultado.
- Remover um arquivo obrigatório deve interromper o processo antes de qualquer gravação.
- O script deve devolver o terminal após a execução.

# SPEC DO ui.py

## Objetivo

Disponibilizar uma interface no navegador para explorar o banco de dados de aviação.

### U1. O QUE FAZ

O arquivo `ui.py` deve:

1. Localizar `aviation.duckdb` na raiz do projeto.
2. Abrir o banco DuckDB.
3. Instalar e carregar a extensão `ui` do DuckDB.
4. Executar `CALL start_ui()`.
5. Disponibilizar a interface em:

`http://localhost:4213`

6. Abrir o navegador automaticamente.

A interface deve permitir explorar os schemas e consultar as tabelas disponíveis.

### U2. FICA DE PÉ ATÉ CTRL+C

A extensão UI permanece ativa enquanto a conexão estiver aberta.

O script deve:

- Manter o processo em execução.
- Informar a URL da interface.
- Exibir a instrução `Ctrl+C para encerrar`.
- Capturar KeyboardInterrupt.
- Fechar a conexão ao encerrar.
- Finalizar sem traceback.

Motivo: o DuckDB utiliza bloqueio de arquivo. Manter o servidor ativo pode impedir outras operações no banco.

### U3. NÃO CRIA BANCO

Se `aviation.duckdb` não existir:

- Exibir mensagem informando que é necessário executar a ingestão primeiro.
- Encerrar com `sys.exit(1)`.
- Não criar um banco vazio.

Motivo: um banco vazio aberto no navegador pode parecer uma ingestão que não funcionou.

### U4. SEPARAÇÃO

O `ui.py` não deve importar `pipeline/ingestao.py`.

A ingestão não deve importar `ui.py`.

A ingestão não deve depender da extensão UI para funcionar.

Motivo: a interface é uma ferramenta de exploração, não uma dependência do pipeline.

### U5. CONEXÃO

A conexão utilizada pela interface deve ser aberta em modo somente leitura sempre que compatível com a extensão UI.

A interface não deve executar transformações ou alterar os dados das tabelas.

### U6. SAÍDA NA TELA

Reconfigurar stdout para UTF-8.

Apresentar:

```text
US Aviation Data Pipeline

Banco: aviation.duckdb
Interface: http://localhost:4213

Pressione Ctrl+C para encerrar.
```

### CRITÉRIOS DE ACEITE — ui.py

- Executar `uv run python ui.py` abre a interface no navegador.
- O schema RAW aparece com as quatro tabelas.
- A interface permite consultar os registros.
- O script permanece ativo enquanto o usuário utiliza a interface.
- Ctrl+C encerra o processo sem traceback.
- Após encerrar a interface, a ingestão consegue acessar o banco sem erro de lock.
- Renomear o banco faz o script apresentar a mensagem de erro sem criar outro arquivo.
